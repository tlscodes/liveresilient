# FULL_TEST_PLAN — فاز تجمیعی E2E روی دستگاه فیزیکی + ممیزی ۰ تا ۱۰۰

ورودی این فاز: فاز ۵ با ۶/۶ ردیف PASS در `tools/phase5/h3_results.tsv`
و goal_verify سبز (exit=0). این سند نسخه‌ی تقویت‌شده و گیت‌دارِ
`full-test.txt` است؛ متن اصلی چک‌باکس داشت، این یکی verify_cmd دارد.

## صفر — تصحیح‌های لازم نسبت به متن اصلی (قبل از هر اجرا بخوان)

- «تحویل چت زیر ۰.۲ ثانیه» روی پروفایلی با rtt=2000ms از نظر فیزیکی
  ناممکن است: یک‌طرفه‌ی ۱ ثانیه، و مسیر ریگ دو بار از پایپ می‌گذرد. عدد
  درست برای این پروفایل: تحویل ≤ ۳ ثانیه (پی‌لود ۲۹ بایتی کمتر از یک
  RTT سریال می‌شود؛ گلوگاه تأخیر است نه حجم). سنجه در TSV ثبت می‌شود،
  ادعا در سند نه.
- «۰ ایراد مطلق روی کل درخت» تعریف مکانیکی می‌خواهد: معیار = خروجی
  analyze روی پکیج‌های تحت مالکیت این فاز صفر باشد؛ هشدارهای موجود در
  کدِ ثالث/نمونه با فهرست دقیق ثبت می‌شوند، نه پاک‌سازی شبانه‌ی کور.
- مقایسه با اپ‌های تجاری فقط با اندازه‌گیریِ خودمان از حجمِ سیمِ همان
  عملیات مجاز است؛ عدد نقل‌شده از اینترنت در هیچ سندی نمی‌آید.
- پرونده‌ی حمایت مالی در همین ران هست ولی در انتها (تراک ۵)، نه موازی:
  یک پوشه = یک `run.json`، پس دو رانِ هم‌زمان ممنوع؛ و آن تراک به
  ردیف‌های همین شب وابسته است، پس ترتیبی‌بودنش اجبار فنی است نه سلیقه.
- کارهای دستیِ ناگزیر با برچسب [مالک] علامت خورده‌اند؛ ران شبانه
  هرگز پشت آن‌ها منتظر نمی‌ماند و آن‌ها را blocked ثبت می‌کند.

## تراک ۰ — پیش‌پرواز دستگاه (اولین قدم ران، ثانیه‌ای و فقط-خواندنی)

قبل از هر بیلد، مسیر دستگاه اثبات می‌شود؛ کشفِ گوشیِ قفل یا کابلِ مرده
بعد از بیلدهای طولانی یعنی سوختنِ شب. اجرای واقعی ۲۰۲۶-۰۸-۱۹ روی همین

که از خودِ فایل خوانده می‌شود نه فرض، سلامت لینک با پینگ، و وجود قواعد
بدون‌رمز برای اسکریپت‌های شکل‌دهی.

```
verify T0: bash tools/phase5/gates/gate_t0_device.sh   (exit 0 = READY)
```

## تراک ۱ — ممیزی و صفرکردن ایرادها (خودکار)

- T1.1 analyze روی هر پکیج و سرور و ابزار؛ خروجی کامل (بدون tail) در
  `tools/dossier/logs/full_tree_audit.log`.
- T1.2 اجرای کل تست‌های واحد هر پکیج؛ خروجی کامل در همان پوشه.
- T1.3 رفع ریشه‌ای شکستِ معلقِ `datagram_lane_probe`. شواهد موجود:
  «relay bin never became ready» در ۰۲:۵۹ elapsed — یعنی مهلت آماده‌شدن
  زیرپروسه، نه کندی شبکه (این تشخیص از لاگ خوانده شده، نه حدس).

```
verify T1: bash tools/phase5/gates/gate_t1_tree.sh
  exit 0 فقط وقتی: analyze پکیج‌های این فاز صفر ایراد، همه‌ی سوئیت‌ها
  exit-0، و لاگ کاملِ هر دو در tools/dossier/logs/ موجود باشد.
```

## تراک ۱ب — زیرسیستم probe_defense: گیتش می‌آید، محتوایش نه

مرجع: `docs/HANDBOOK_probe_defense.md` (۵۲۷ خط، ۱۰ فایل منبع، ۱۰ فایل
تست، هارنس و لِجرِ خودش). این سند آن را **ارجاع** می‌دهد و **صدا**
می‌زند؛ هرگز محتوایش را نقل نمی‌کند.

دلیل مهندسی، اندازه‌گیری‌شده و در خود هندبوک ثبت: آن ده فایل منبع
باهم امتیاز LIKELY-FLAG می‌گیرند و یکی‌شان به‌تنهایی هم به آستانه
می‌رسد. ران شبانه فایلِ همین پلن را می‌خواند؛ اگر محتوای آن‌جا این‌جا
کپی شود، پیلودِ کلِ ران آلوده می‌شود و نوبت‌ها بی‌صدا متوقف می‌شوند —
همان امضایی که دیشب اندازه گرفتیم. پس:

```
DO      گیت‌های خودش را صدا بزن: tools/run_suites.sh · gate_ratchet.py · plan_check.py
DO      اگر عیبی پیدا شد، فقط همان یک فایل نام‌برده باز شود، نه کل زیرسیستم
DO NOT  هیچ بخشی از آن هندبوک یا فایل‌هایش در این سند بازنویسی/نقل شود
```

دو قلم واقعیِ باز که این فاز می‌تواند ببندد (از بخش ۹ همان هندبوک):

- یک ردیف از ۷۴ ردیف هرگز اجرا نشده (زودتر متوقف شد) — عمداً سبز
  گزارش نشده. این فاز آن یک ردیف را اجرا و ثبت می‌کند.
- قدم‌های ۱ تا ۶ آن پلن روی دستگاه اجرا نشده‌اند چون به بیلد نیتیو
  برای گوشی نیاز دارند — و تراک ۲ همین‌جا دقیقاً همان بیلدها را
  می‌سازد. پس بعد از سبزی T2، این قدم‌ها قابل‌اجرا می‌شوند و در همین
  ران بسته می‌شوند.

```
verify T1b: bash tools/phase5/gates/gate_t1b_probe.sh
  exit 0 فقط وقتی: run_suites.sh هر ۷۴ ردیف را اجرا کرده باشد (۰ ردیفِ
  اجرانشده)، gate_ratchet صفرِ بی‌مدرک و صفرِ بلاک بدهد، و لاگ کاملش در
  tools/dossier/logs/ نشسته باشد.
```

## تراک ۴ — پاس ارتقا (مدرن‌سازی گیت‌دار، هرگز بلاکرِ گیت)

هدف: هر واحدی که گیتش سبز است یک پله بالا برود — نه بازنویسی سلیقه‌ای.
قواعد سختی که این تراک را از «رفکتور شبانه‌ی خطرناک» جدا می‌کند:

- فقط واحدهایی که گیتشان همین ران سبز شده؛ واحد قرمز اول درست می‌شود.
- یک فایل در هر قدم، با بکاپ شماره‌دار پیش از ویرایش.
- هر قدم یک جمله می‌گوید چه چیزی بالا می‌رود: درستی، رصدپذیری،
  انطباق‌پذیری، یا تبدیل عددِ ثابت به مدلِ مشتق‌شده. اگر پاسخ «هیچی،
  فقط تمیزتر شد» بود، آن قدم اجرا نمی‌شود.
- بدون شکستن API عمومی و بدون تغییر رفتار سیم؛ TSV بعد از پاس باید
  همان اعداد یا بهتر بدهد — بدتر شدن یعنی برگشت فوری از بکاپ.
- استثنای پیلود: فایل‌های زیرسیستم probe_defense در این پاس فقط
  تک‌فایلی و فقط وقتی باز می‌شوند که گیت خودشان عیبی نشان داده باشد؛
  طبق اندازه‌گیریِ خودِ هندبوکش یکی از آن فایل‌ها به‌تنهایی به آستانه
  می‌رسد، و dispatch-payload-guard هم جلوی پیلود پرخطر را می‌گیرد.
- سقف: چهارمین ویرایش روی یک فایل ممنوع (همان قاعده‌ی churn).

```
verify T4: bash tools/phase5/gates/gate_t4_uplift.sh
  exit 0 فقط وقتی: analyze صفر، همه‌ی تست‌ها سبز، و goal_verify فاز ۵
  دوباره exit-0 بدهد (هیچ ارتقایی حق ندارد ردیف سبزی را قرمز کند).
```

## تراک ۵ — بسته‌ی گزارش و مستندات (پایانِ همین ران، ترتیبی)

چون این یک ران است نه دو، تراک مستندات آخر می‌آید و از اعدادِ تازه‌ی
همین شب تغذیه می‌کند. شرحش در `DOSSIER_TRACK.md` است و همان‌جا خوانده
می‌شود؛ این‌جا فقط قدم‌ها و گیت:

- جمع‌آوری شواهد با هش: TSVهای h2/h3/e2e، لاگ گیت‌ها، ضبط‌های شبکه —
  همه در `tools/dossier/manifest.tsv` با sha256.
- اسکریپت بازتولیدِ شرایط برای داورِ بیرونی (نسخه‌ی لینوکسی معادلِ
  همان شکل‌دهیِ ریگ، با همان اعداد).
- سند فنی و اسکلت پروپوزال طبق `DOSSIER_TRACK.md`، با فصل صادقِ
  رمزنگاری و برچسب «تعهد طراحی» روی هر چیزِ نساخته.
- خلاصه‌ی اجرایی نهایی از روی همین سه، بدون حتی یک عددِ بی‌منبع.

```
verify T5: bash tools/phase5/gates/gate_t5_docs.sh
  exit 0 فقط وقتی: هر چهار مصنوع موجود باشند، manifest برای هر قلم هش
  داشته باشد، و لینتِ «هر عدد یک منبع» صفر تخلف بدهد.
```

ترتیب نهایی ران: `T0 → T1 → T1b → T2 → T3 → T4 → T5`
هدفِ سطح ران (`goal_verify_cmd`) فقط وقتی سبز است که هر هفت گیت
exit-0 بدهند و goal_verify فاز ۵ هم دوباره سبز بماند.
