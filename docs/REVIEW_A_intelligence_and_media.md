بخشِ اولِ دو بخش. این پرونده خودبسنده است و برای داوری در یک نشستِ مستقل

مرجعِ کاملِ شش‌تیکتی: `docs/PLAN_five_tickets_v1.md`.

## ۱. مرزِ معماری میانِ هوشمندی v4 و کارهای امنیتی

**حکمِ پیشنهادی: جدا، با دو درزِ یک‌طرفه.** سه دلیل.

**یکم، تعریفِ امتیاز.** امتیازِ v4 میانگینِ چهار مؤلفه است و مقایسه‌پذیریِ
v4≥v3 روی ثابت‌ماندنِ همین تعریف بنا شده. سندِ طراحی این تصمیم را قبلاً
یک‌بار گرفته:

```
docs/DESIGN_intelligence_v4.md:143-144
      گذار فیلد گزارشی نو می‌گیرد، نه جزء میانگین چهارتایی
      (تعریف score برای مقایسه‌پذیری v4>=v3 ثابت می‌ماند)
```

مدلِ گذارِ ستون ۴ عمداً بیرونِ میانگین ماند. اگر پارامترهای شکل‌دهی داخلِ
امتیاز بروند، بازپخشِ روی کورپوس — تنها دروازه‌ی رگرسیونِ هوشمندی — معنا
از دست می‌دهد و عددِ ۱٫۱۰۷ دیگر با ۱٫۰۸۵ قابلِ مقایسه نیست.

**دوم، یک شکل‌دهنده‌ی یادگیرنده خودش نشت است.** کلِ ادعای تیکت ۱ استقلالِ
خروجی از محتوا و شرایط است. اگر پارامترهای لایی و گام را یک یادگیرنده از
مشاهدات تنظیم کند، خروجی دوباره تابعِ مشاهدات می‌شود. این نقضِ مستقیمِ
خاصیتی است که تیکت ۱ می‌خواهد اثبات کند، نه یک ترجیحِ سلیقه‌ای.

**سوم، معناشناسیِ بازگشتِ نسل فرق می‌کند.** حلقه‌ی قهرمان/چالش‌گر وقتی
امتیاز افت کند مغز را به نسلِ قبل برمی‌گرداند. بایت‌های لایی و فریم‌های
پوششی همیشه پهنای‌باند مصرف می‌کنند و هیچ‌وقت تأخیر را کم نمی‌کنند، پس در
هر سنجه‌ای که این حلقه بهینه می‌کند، پیکربندیِ بدونِ لایی امتیازِ بالاتری
می‌گیرد. نتیجه مکانیکی است: حلقه پیکربندیِ بدونِ لایی را ترفیع می‌دهد و
پیکربندیِ لایی‌دار را برمی‌گرداند، بدونِ اینکه کسی چنین تصمیمی گرفته باشد.
بنابراین پارامترهای لایی نباید در دامنه‌ی این بهینه‌سازی باشند.

**دو درزِ مجاز، هر دو یک‌طرفه و خواندنی:**

```
seam 1  budget    سقف/کفِ گامِ تیکت ۲ از budget_calibrator.budgetQuantile می‌خواند
seam 2  pre-warm  تیکت ۳ از likelyNextNetwork می‌خواند (جزئیات در پرونده‌ی ب)
```

هیچ سنجه‌ای از این کارها به میانگینِ چهارتایی برنمی‌گردد.

هر هشت ترکیب از سقفِ ۰٫۷ عبور می‌کند. همان حساب با سربارِ درست به اشغالِ

فایل می‌گویند نبودش تماس را کشت.

### راهکار

```
1a  افزودنِ cbr به OpusSdpPolicy و نوشتنِ cbr=1 در fmtp
1b  headerBitsPerPacket از ثابت به تابعی از حاملِ انتخاب‌شده
1c  lengthBuckets از هیستوگرامِ پیکربندی‌پذیر، نه ثابتِ خطِ 80
1d  زمان‌بندِ مستقل داخلِ traffic_shaper.dart — تیکِ ثابت، و در صفِ خالی
    یک فریمِ ساختگیِ هم‌شکل
1e  DTX دیگر ثابت نیست: تابعِ وضعیتِ شکل‌دهی
```

جایِ گامِ ۱-د `traffic_shaper.dart` است، نه `binary_stream_transfer.dart`؛
بریفِ اصلی فایلِ اشتباه را نام برده بود.

### سیاستِ DTX

```
shaping ON  (لینکِ عادی)          cbr = true   dtx = false   جریانِ یکنواخت
shaping OFF (لینکِ باریک/اضطراری)  cbr = false  dtx = true    بقایِ تماس مقدم است
```

هر دو کلید از یک تصمیمِ خاموشی تبعیت می‌کنند تا نتوانند ناسازگار تنظیم
شوند.

### دروازه‌ی مکانیکی

```
1a  دو ران SLA پروفایل narrow و bandwidth با CBR روشن و DTX خاموش، سبز
1b  تستِ واحد: اشغال <= 0.7 روی هر هشت ردیفِ جدولِ بالا با سربارِ 66 بایت
1c  K-S روی هیستوگرامِ طول، سطحِ 0.05
1d  K-S روی توزیعِ زمانِ بین‌ورود، مقایسه‌ی پنجره‌ی سکوت با پنجره‌ی صحبت،
    سطحِ 0.05 — بدونِ زمان‌بندِ مستقل باید قرمز شود
1e  تستِ واحد: shaping OFF -> dtx true و cbr false؛ shaping ON -> عکسش
regression  packages/messaging 46 tests + packages/media_webrtc تست‌ها سبز بمانند
```

## تیکت ۲ — سقف و کفِ گامِ زمان‌بند

### مسئله

اشکالِ یکم، ابعادی. بودجه‌ی ۱۵۰ میلی‌ثانیه‌ی تعاملی یک‌طرفه است و
`conditions.rtt` رفت‌وبرگشت. با فرمولِ بریف، از rtt حدودِ ۳۰۰ms به بالا
خروجی منفی است؛ گریدی که خودِ بریف نام می‌برد تا ۲۰۰۰ms می‌رود.

اشکالِ دوم، جهتِ فرمول با قراردادِ ثبت‌شده‌ی همان کلاس مخالف است:

```

      "a shaped link only ever gets MORE patience"
packages/call_core/lib/src/connection_budget.dart:67    minRtt        = 200ms
packages/call_core/lib/src/connection_budget.dart:102   maxElapsedCap = 450s
packages/call_core/lib/src/connection_budget.dart:107   maxLossFactor = 8.0
packages/call_core/lib/src/connection_budget.dart:311   heartbeatLinkShare = 0.05
```

سقفِ گام برعکس عمل می‌کند: لینکِ بدتر، گامِ کوچک‌تر، فریمِ پوششیِ بیشتر —
روی همان لینکی که تیکت ۱ نشان داد جا ندارد.

نکته‌ی کمّی که اندازه‌ی تیکت را کوچک می‌کند:

```

traffic_shaper.dart:131   maxJitter = 8000 us    (پیش‌فرضِ aggressive)
```

بودجه‌ی ۱۵۰ میلی‌ثانیه ده‌ها برابرِ این است؛ پس این سقف امروز روی هیچ‌چیز
مقید نیست و فقط برایِ زمان‌بندِ مستقلِ گامِ ۱-د معنا دارد. تیکت ۱ و ۲ یک
تیکت‌اند.

### راهکار

```
step_max = 150ms - rtt/2 - T_jitterbuf
step_min = frameBits / (0.7*bw - audioWireRate)
```

اگر بازه تهی شد، پاسخ «شکل‌دهی روی این لینک خاموش» است، نه یک عددِ کف — و
طبقِ جدولِ سیاستِ تیکت ۱ همان خاموشی DTX را برمی‌گرداند. این همان قیدِ
خاموش‌شدن روی لینکِ باریک است که در `RIG_GUIDE.md` بخشِ ۶ ثبت شده.

اتصال به v4 از راهِ درزِ یکم:

```

packages/connection_orchestrator/lib/src/budget_calibrator.dart:170  double budgetQuantile({...})
docs/DESIGN_intelligence_v4.md:48-50   p80 چندکِ بودجه است، نه تخمین‌گر نقطه‌ای
```

سندِ طراحی صریح می‌گوید p80 در نقشِ تصحیح مؤلفه را به ۰٫۵۴ می‌اندازد ولی
در نقشِ بودجه درست است.

### دروازه‌ی مکانیکی

```
2a  گریدِ کاملِ rtt 4..2000ms و loss 0..0.9 — خروجی همیشه در [step_min, 150ms]
    یا صریحاً «خاموش»؛ هرگز منفی و هرگز صفر
2b  تستِ یکپارچگی: مقدارِ برگشتی توسطِ زمان‌بندِ گامِ ۱-د مصرف شود

```

## موجِ اتمی — ترتیبِ اجرای این دو تیکت

```
یا هر چهار قلم با هم می‌روند یا هیچ‌کدام:
  1a  CBR روشن، DTX تابعِ شکل‌دهی
  1b  سربارِ پویا
  1d  زمان‌بندِ مستقل
  2   متدِ دوطرفه‌ی سقف/کف با قاعده‌ی خاموشی
commit-gate: تا هر چهار دروازه سبز نشوند، شاخه merge نمی‌شود.
```

چرا اتمی: CBR بدونِ سربارِ درست، لینکِ باریک را اشباع می‌کند؛ و زمان‌بندِ
مستقل بدونِ قاعده‌ی خاموشیِ تیکت ۲ همان اشباع را از راهِ فریمِ پوششی
می‌سازد. آنچه لینکِ باریک را نجات می‌دهد قاعده‌ی خاموشی است، نه خودِ
زمان‌بند — زمان‌بند مصرف را بالا می‌برد. پس شرطِ ایمنی این است که زمان‌بند
هرگز پیش از قاعده‌ی خاموشی مستقر نشود.

گامِ ۱-ج بعد از پایداریِ این موج می‌رود؛ بی‌خطر است.

## آنچه از تو می‌خواهم — سه داوری و یک بازبینی

نقشِ تو داورِ معماری است، نه مجری. هیچ فایلی را ویرایش نکن.

**داوریِ ۱ — مرزِ معماری.** بخشِ ۱ را تأیید می‌کنی؟ اگر نه، کدام دلیل را
رد می‌کنی و تعریفِ جایگزینِ امتیاز چیست؟

**داوریِ ۲ — سیاستِ لینکِ باریک.** جدولِ اشغال نشان می‌دهد روی ۱۶ کیلوبیت
با دو جریان جا نیست. دو گزینه: تنزیلِ درجه‌بندی‌شده (استقلالِ زمان قربانیِ
بقایِ تماس، DTX برمی‌گردد) یا قطعِ سخت (تماس روی چنین لینکی برقرار نشود).
کدام و چرا؟

**داوریِ ۳ — اتمی بودنِ موج.** آیا واقعاً باید اتمی باشد یا می‌شود امن‌تر
تکه‌اش کرد؟ اگر یکی از چهار قلم در آخرین لحظه شکست بخورد، بازگشت چگونه
است؟

**بازبینی — نقصِ خودِ پرونده.** فرض کن این تحلیل غلط است و دنبالِ اشتباه
بگرد. مشخصاً: کدام دروازه چیزی را که ادعا می‌کند اثبات نمی‌کند؟ دروازه‌ی
۱-د که سکوت را با صحبت مقایسه می‌کند واقعاً کافی است؟ آیا ادعایی هست که
پشتوانه‌ی اندازه‌گیری ندارد و علامت نخورده؟

قواعدِ خروجی: هر حکم با دلیل؛ هر ارجاعِ کدی با file:line؛ مخالفت با یک
عدد فقط با نامِ اندازه‌گیریِ ناقض؛ جایی که داده کافی نیست بنویس «کافی
نیست» و بگو چه اندازه‌گیری‌ای لازم است؛ پرونده را بازنویسی نکن.

- هیچ‌یک از این گام‌ها اجرا نشده؛ هیچ ویرایشی روی کدِ مخزن انجام نشد.
- جدولِ اشغال خروجیِ اجرایِ واقعیِ یک اسکریپت است، ولی حسابِ سربارِ ۶۶
  بایت از مستندات مشتق شده نه از یک ضبطِ واقعی.
- `sentinelLeadMs` هنوز null است (`RIG_GUIDE.md` خطوطِ ۱۷۹-۱۸۰)؛ هیچ
  ادعایی به آن تکیه نمی‌کند.
