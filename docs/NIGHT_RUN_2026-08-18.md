## The thing worth waking up for

The cross-architecture comparison found a defect that had been invisible for a
day, on its first run.

`tools/first_record_dump` carried an inline copy of the measurement program —
an OLDER one. The extraction into `tools/first_record/first_record.c` had
happened, the comment explaining why the extraction mattered had been written,
and the old copy had never been deleted. So every capture compiled a program
missing four configuration calls that the documented instrument makes.

```
before  11 extensions, 16 ciphers incl. 0xc009 0xc00a   1488 bytes
after   17 extensions, those two ciphers absent          1533 bytes
```

Nothing caught it, because the captured record's only reader was a comparison
against a profile derived from that same capture — the measurement was agreeing
with itself. It surfaced within minutes of a second machine composing the same
record through an independent implementation, and the two disagreeing on exactly
those four extensions.

The runner now stages the real file. `docs/TICKET4_FIRST_RECORD/RESULT.md` says
this in place, and the general lesson is in the knowledge tree.

## Both architectures, and what that word now rests on

```
docs/evidence/first_record_x86_64.txt   1533 bytes  Darwin x86_64
docs/evidence/first_record_arm64.txt    1533 bytes  iOS 26.0, ios_arm64
python3 tools/compare_arch_records.py --require-arch arm64
  ->  ARCH COMPARE PASSED
```

The comparison is not a diff and could not be: the configuration permutes its
extension order per connection and fills several fields with fresh random
material, so two runs on ONE machine already differ byte for byte. What is
compared is a committed projection — `docs/evidence/first_record_projection.json`
names each invariant field and why, and names the variant ones too. The
comparator also refuses a candidate that does not declare the architecture being
claimed, and refuses two records from the same architecture, because with the
projection alone a second host run would pass as a phone run.

The arm64 side did not come from a re-run of the host tool. It came from an
integration test that asks the phone's own process, through a shim linked into
the app, which is why it counts as an independent implementation rather than the
same program on another machine.

### What was then done with that answer

The second member was added — the deliberate, dated act the type's own doc
comment has described since it was written — and the compile-time break fired
for the first time in its life: this package's gate test, the app's wording
function and the app's surface test all stopped compiling within seconds. Each
was revisited, which is the entire mechanism.

```
+ NativeShapePresent, carrying the revision the MODULE reported
+ NativeShapeProbeReport, so a yes arrives WITH provenance
~ the resolver refuses a yes that carries no revision
- probeSucceededButPresentStateNotRepresentable — the member named for an
  impossibility that ended — replaced by probeNotRun
~ the build constant now says "nothing has asked", not "the capability is
  absent", because on a device build the second sentence is false
```

Two gates were rewritten, and that is the reason this sits on a branch. 4d used
to prove "one member, so available is unrepresentable"; it now proves "two
members, and the available one is constructed in exactly ONE place — the
resolver". 4e used to require the words "not available" from every cause;
`probeNotRun` does not mean that, so it now requires every absent cause to
decline the claim, and a new case requires the available sentence to name the
revision it rests on. The subject of both gates is unchanged — an available
answer must be impossible to manufacture — but changing what a gate asserts is
a decision that deserves your eye, not mine at four in the morning.

### The one thing that went wrong tonight, and what caught it

Trying to put the 4a closure on `main` as well, I switched branches with a dirty
tree — and that reverted 25 files that had been sitting modified-but-uncommitted
here from earlier sessions, because tonight's migration commit had staged by
directory and swept them onto the branch.

The ratchet caught the first half in under a minute: gates 6a and 6g stopped
being proven, since their tests live in the uncommitted half of
`ws_connector_test.dart`. Restoring those 25 modified files was not enough — the
suite then found the second half, because 95 further files had gone from
untracked to tracked on the branch and were therefore DELETED by the switch,
including a source file `adaptive_transport`'s barrel exports. Both passes are
committed (`30b8d68`, `cd5f2ac`) and the tree is back to what it was, now with
that work committed where it lives so a switch cannot decide its fate again.

Two checks found this, and neither was looking for it: a ledger that fails when
something that WAS proven stops being proven, and a suite run that compiles
every package. The lesson is in the commit messages and in the knowledge tree:
stage by file when the tree carries work that is not yours.

Five goldens moved with it (the panel's sentence grew from four lines to six).
The master and test renders were compared before any baseline was replaced:
identical header, tiles and sparklines, one longer text block, nothing else.

The old reasoning for not proceeding immediately, kept because it was true when
it was written and because the sequence matters:

`applied` means the peer honoured the configuration this build offered — not
merely that a session completed. The probe distinguishes those two, on purpose:
a session that completes while the peer ignores the configuration is the
near-miss that would otherwise be reported as success.

The phone's `unreachable` is about reaching this host, not about the module: the
same function, on the same build, reports the backend linked and reads its pin
correctly, and the phone composed a first record through it minutes earlier. The
host is at `192.168.1.176`, its firewall is off, and the helper is listening —
this machine connects to its own LAN address happily.

**Two candidate causes, and I fixed one of them.** The app's `Info.plist` had no
`NSLocalNetworkUsageDescription`, and since iOS 14 an app that connects to a
local-network address without it is refused by the system — which surfaces at
the socket exactly as unreachable. The key is now there. The first run after
that will raise the system's local-network prompt, and **somebody has to tap
Allow**; an unattended test cannot. The second candidate is the ordinary one:
this Mac's Wi-Fi carries no address (the route lives on a wired interface), so
if the phone is on Wi-Fi or cellular it is on a different network from
`192.168.1.176`.

I could not tell these two apart while you slept — granting the prompt needs a
tap and changing the machine's network settings is not mine to do. The morning
sequence below separates them in one run: if the prompt appears, it was the
declaration; if no prompt appears and it still says unreachable, it is the
network.

The type's own rule is what kept me from proceeding anyway
(`native_shape_availability.dart:86-97`): an available result may only come from
a probe that observed the module working **on the device that is running**. A
host-side `applied` is not that. Adding the second member on the strength of it
would put a claim in the type that the device has not made.

So the migration is prepared but not performed, and nothing was merged while
nobody was awake.

## Step 7 — the capture, and the one line only you can write

The script is written, committed and syntax-checked:
`tools/t2/step7_trace.sh`. It attaches a trace interface to the phone, captures
for a bounded time, and writes a provenance header beside the capture. It needs
root, which means a rule that does not exist yet.

```bash
sudo visudo -f /etc/sudoers.d/t2rig-extra
```

with one line inside:

```
behnam ALL=(root) NOPASSWD: /Users/behnam/Downloads/voice_call_kit_v3/tools/t2/step7_trace.sh
```

Then it is always called as `sudo -n`, so a missing rule fails loudly instead of
hanging a run behind a prompt. What that grant means is written in the script's
own header, including the part worth knowing: the file is writable by your user,
so anything running as you can reach root through it — a deliberate trade on a
single-user development machine, with the stricter alternative named.

Step 7 also depends on step 6, because there is nothing to capture until the
phone actually makes the connection.

## What is NOT claimed

- **Gate 4a is closed on a recorded run, not on a live one.** The suite cannot
  re-perform it: the measurement needs a phone, a helper process and a cable.
  What the suite holds is the recorded run's own words —
  `ticket4_device_probe_test.dart` fails if the evidence stops saying `applied`,
  and its negative control rejects `ignored`, the outcome where the exchange
  finishes and the peer does nothing. Re-running it live is one command.
- **Gate 4b is not closed** and could not be: no capture exists.
- **The probe measured one peer, once.** It says a peer that speaks the
  extension honoured this build's configuration. It says nothing about what any
  other server would do, and nothing about what a middlebox on a real path
  would see — that is 4b's job.
- **The host probe used a peer whose certificate no authority signed.** The
  probe deliberately does not check credentials, which is why it is named as a
  probe, takes no payload and returns no connection. It measures the extension
  and nothing else.
- **The shim duplicates the instrument's configuration.** `pt_shim.c` mirrors
  `first_record.c` call for call rather than sharing one source. The duplicate
  is guarded by the very comparison that found tonight's defect, and the
  single-source version is the better end state — not taken tonight because
  changing the instrument that produced the baseline, in the same session that
  compares against that baseline, would invalidate the comparison.
- **This working tree carried uncommitted changes from earlier sessions** in
  files tonight's commits also touched. They are named in the commit messages.
  They were not reviewed line by line.
