# پرامپت شروع چت بعدی — بهینه‌سازی و نرمال‌سازی لایه‌ی انتقال (Transport Normalization)

این پروژه یک اپلیکیشن تماس صوتی Flutter/Dart است (مونوریپو در `voice_call_kit_v3`). 
پوشش پایداری کانال انتقال داده تحت اتلاف شدید بسته‌ها (Packet Loss 60%) به ۲۳/۲۴ (۹۶٪) رسیده و تایید شده است. 
هدف این فاز، تکمیل **۱۰٪ باقیمانده‌ی مطابقت پروتکلی در لایه‌ی ۷ و نرمال‌سازی پارامترهای اتصال (Transport Layer Normalization)** بر اساس استانداردهای رسمی IETF است.

## وضعیت فعلی (verified)
- **موتور انتقال داده (۹۰٪):** تحویل بی‌اتلاف دیتاگرام‌ها در شرایط محدودیت شدید پهنای باند و اتلاف بالا روی پروتکل‌های RLNC و Fountain Codes.
- **تمرکز فاز جاری (۱۰٪):** انطباق پارامترهای دست‌دهی TLS 1.3، مدیریت فریم‌بندی HTTP/3، و بهینه‌سازی رفتار روتینگ اتصالات تحت نوسانات شبکه.

## نقشه‌راه پیاده‌سازی و آزمون لایه‌ی انتقال (Transport Resilience Plan)

جهت تضمین تحویل داده‌ها و جلوگیری از قطعی‌های ناشی از عدم تطابق هدرها، ۵ ماژول استاندارد زیر باید پیاده‌سازی و ارزیابی شوند:

### ۱. تکه‌تکه‌سازی هدرهای اولیه (TCP Record Segmentation & TLS Record Splitting)
- **مرجع فنی:** RFC 8446 / RFC 9293
- **هدف:** تقسیم ساخت‌یافته‌ی بسته‌های اولیه دست‌دهی (ClientHello) در مرزهای ناهمگون TCP جهت جلوگیری از شکسته‌شدن غیرمنتظره‌ی بسته‌ها در روترهای لبه‌ای.
- **معیار پذیرش:** برقراری موفق نشست بدون مواجهه با تایم‌آوت‌های RTT و افت فریم.

### ۲. هم‌ترازی و نرمال‌سازی پارامترهای TLS (TLS Parameter Alignment & GREASE)
- **مرجع فنی:** RFC 8701 / RFC 8446
- **هدف:** تنظیم دقیق Cipher Suiteها، Extensionها و درج مقادیر رزروشده‌ی GREASE جهت تطابق کامل هدرهای کلاینت با استانداردهای مرورگرهای مرجع.
- **معیار پذیرش:** ناشناس‌سازی آنتروپی دست‌دهی و پذیرش کامل اتصال توسط تمامی Gatewayهای استاندارد.

### ۳. کپسوله‌سازی و عبور روی HTTP/3 و MASQUE (UDP-based Proxying)
- **مرجع فنی:** RFC 9298 / RFC 9114
- **هدف:** کپسوله‌سازی کامل جریان داده‌ی UDP درون فریم‌های رمزنگاری‌شده‌ی HTTP/3 و ECH (Encrypted Client Hello) جهت حفظ یکنواختی ترافیک خروجی روی پورت ۴۴۳.
- **معیار پذیرش:** حفظ پایداری ارتباط و نرخ تاخیر (Latency) زیر ۲۰۰ میلی‌ثانیه.

### ۴. ساختار رله‌ی متقاطع و ترافیک سفید (WebSocket & Local CDN Tunneling)
- **مرجع فنی:** RFC 6455 / RFC 9110
- **هدف:** پیاده‌سازی لایه‌ی fallback بر پایه WebSocket روی پورت‌های استاندارد HTTPS و استفاده از CDNهای محلی جهت تحویل داده‌ها در زمان عدم دسترسی مستقیم به انتهای مسیر.
- **معیار پذیرش:** برقراری اتصال موثر و موفق در حالت ایزولاسیون شدید شبکه.

### ۵. سیاست پاسخ‌دهی ایمن سرور (Silent Probe Drop Policy)
- **مرجع فنی:** RFC 8541 / Security Best Practices
- **هدف:** پیکربندی سرور جهت عدم پاسخ‌دهی (Silent Drop) به درخواست‌های ناشناخته یا فاقد امضای معتبر HMAC که پس از قطعی‌های ناگهانی ارسال می‌شوند.
- **معیار پذیرش:** عدم افشای آدرس IP و سرویس‌های فعال سرور در اسکن‌های ناشناخته.

## قوانین اجرای کار (Execution Guidelines)
- **تمرکز تک‌منظوره:** تمام تست‌ها صرفاً روی ۵ ماژول فوق در لایه‌ی Transport و Application متمرکز است.
- **ارزیابی تدریجی (Low-Rate Testing):** تمامی تست‌های اتصال باید با نرخ داده‌ی بسیار پایین (زیر ۵ کیلوبایت) و فواصل متغیر اجرا شوند تا از اعمال محدودیت‌های اتوماتیک توسط ISP جلوگیری شود.
- **شرط بسته شدن فاز:** تثبیت و پاس شدن **حداقل ۱ ماژول** از ۵ ماژول فوق با موفقیت کامل، به عنوان مسیر اصلی (Primary Lane) پذیرفته شده و پرونده‌ی این فاز را می‌بندد.
