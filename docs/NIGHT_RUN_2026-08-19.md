# Night run, 2026-08-19 — read this first

## The one-paragraph version

Two tests had been flaking. A handoff note called both of them "load-sensitive
time-budget tests" and that description was acted on directly, without anyone opening
the logs. When the logs were finally opened, the two failures had **different causes**,
and only one of them was about machine load. The crypto-admission test really was
load-sensitive and is now rebuilt to be immune, verified under full CPU saturation and
verified to still catch a real regression. The video-transfer test was never slowed by
load at all — its failure was a helper process that took longer than 60 seconds to
start when twenty-two compiles competed for four cores. Separately, three hooks were
installed so this class of mistake cannot repeat: Claude Code now refuses to edit code
while an unread failing log exists in the repo, and it prints the lessons index at the
start of every session.

## 1. Crypto admission test — DONE, committed 012901f

`packages/adaptive_transport/test/probe_defense/relay_key_rotation_test.dart`

The old assertion was an absolute microsecond budget with a best-of-five-rounds
defence. That defence was itself inflated 2.46x by host load in the failing run. It was
replaced, not widened.

**Structure is read, not timed.** `EpochAdmission.keysTried` already reports how many
keys the admission path tried. The claim was being estimated from a duration ratio
whose band was narrower than its own noise; it is now two exact assertions.

**Magnitude uses one-sided noise.** The scheduler only ever adds time, so the minimum
over individually timed samples converges to the true cost from above. The asserted
statistic is the ratio of two minima — cleanest admission over cleanest keygen.

```
healthy      4.22 unloaded · 4.18 / 4.20 / 4.21 with every core saturated
             spread 1.007x
diagnostic   per-round PHASE ratios in those same runs: 1.30 .. 8.44, spread 6.5x
             kept in the evidence line, deliberately NOT asserted
bounds       upper 6.45 = midpoint(4.20 healthy, 8.69 measured-doubled)
             lower 2.25 = midpoint(4.20 healthy, 0.3 ESTIMATED and labeled so)
power        regression injected -> 8.56, RED against 6.45; file restored, sha match
```

An intermediate version asserted the phase ratio. A healthy round of 1.30 would have
turned it red — which is exactly why the diagnostic is not an assertion.

## 2. Video-transfer test — the real defect is still open

`apps/reference_app/test/datagram_lane_probe_test.dart`

Uncommitted changes exist on this file and they are defensible on their own argument:
the old 8-minute deadline conflated "the host was busy" with "the transport stalled",
and it is now split into a progress watchdog plus load-independent assertions on
symbol overhead and paced rate. Both a baseline and a fully saturated run pass.

But that is **not** the defect that was failing. The 60-second readiness timeout is,
and it is being root-caused by a multi-agent pass whose result is pending. Nothing on
this file is committed until that lands, so the tree still shows it as modified.

**A measurement that rules out the simplest story.** Spawning the relay by hand while
a full suite run loaded the machine:

```
run1  ready in 5.67s   load average 70.95
run2  ready in 3.59s   load average 78.00
run3  ready in 3.27s   load average 95.63     the test allows 60s
```

So a warm relay starts in about four seconds even at twenty-times oversubscription.
CPU contention alone cannot produce a 60-second miss, and any fix that merely scales
the timeout with load would be built on the same kind of unverified story this report
is about. The remaining candidate is a COLD start: `server/signaling_server/bin/
datagram_relay.dart` is still untracked in git, so in the failing run it may have been
newly added, forcing a full dependency resolve and compile with nothing on stdout while
it worked. Testing that means clearing `.dart_tool` for that package, which the running
suite is currently using — so it is queued behind the suite rather than guessed at.

## 3. The mistake is now mechanically prevented

```
PreToolUse   evidence-gate-guard.py     blocks Edit/Write while a fresh (<48h),
                                        failing, UNREAD log exists under cwd
PostToolUse  evidence-gate-record.py    a Read, or a Bash command naming the path,
                                        marks it read — keyed to content signature,
                                        so a regenerated red log re-arms it
SessionStart knowledge-index-boot.py    newest-first lessons index, capped at
                                        30 entries / 4000 chars
```

```
python3 ~/.claude/scripts/test_evidence_gate.py   ->  EVIDENCE GATE PASSED (0 failures)
guard marginal cost                                   21 ms  (193.6 guarded - 172.5 bare)
```

That 21 ms is itself a paired measurement against a same-host reference, because the
raw wall time of 364 ms was almost entirely Python interpreter startup — the same
mistake in miniature, caught by the same rule.

What the gate cannot do, stated plainly: it forces the failure message into the
transcript, not into the reasoning. Reading the log and still believing the wrong
hypothesis remains possible.
